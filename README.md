# Hayabuzz — サーバレスP2P早押しクイズ

GitHub Pages（静的配信のみ）でホストできる早押しクイズアプリです。バックエンドは持たず、
通信は WebRTC DataChannel による P2P で行います。P2P 層（WebRTC ハンドシェイクと
シグナリング）は外部ライブラリに依存せず自前実装です。

シグナリングには WebTorrent トラッカーの WebSocket プロトコルを使います:
公開トラッカーへ部屋名のハッシュ（info_hash）で announce し、メッセージに相乗りさせた
WebRTC の offer/answer（SDP テキスト）を同じ部屋の相手と交換します。トラッカーを通るのは
この接続情報だけで、接続確立後のゲームデータは端末間の DataChannel を直接流れます
（トラッカーが必要なのは参加の瞬間だけ。ゲーム中に落ちても進行に影響しません）。

## 遊び方

1. 出題者がトップ画面から「出題者として部屋を作る」を選ぶ
2. 開いた共有ポップアップのルームコード / URL / QRコードを回答者に共有し、
   集まったらポップアップを閉じて出題へ（ヘッダーの「共有」からいつでも再表示できる。
   参加は途中でも受け付ける）
3. 回答者はニックネームを入力して参加。画面の大半が早押しボタンになる
   （「設定」からボタンの見た目 9 種類と効果音の ON/OFF を変更できる。設定は端末ローカルに保存）
4. 出題者は「① 問題を用意 → ② 全員に出題 → ③ 早押し受付 → ④ 判定」の4ステップで進めます。
   出題カードに現在地とヒントが出て、次に押すボタンが強調されます
   （問題を出しただけではまだ押せません。全員が読んでから「早押し開始」で受付を始めます）
   （参加者と得点は画面下のシートに収納。取っ手をタップするとせり上がり、
   閉じていても取っ手に参加人数とチーム合計が出る。履歴・結果発表・得点リセットもこの中）
5. 不正解時は「次点へ権利を回す」「全員に再開放（誤答者は除外）」を選べる
   （ゲームの締めは「結果発表」で全端末に最終ランキングを表示。得点リセットで再戦できる。
   終わったら「設定 → 部屋を閉じる」で回答者に終了を伝えてトップへ戻る）
   - 出題者がうっかりリロードしたり、タブを閉じてしまっても、トップ画面の
     「前の部屋に戻る」から同じ部屋に復帰できる（参加者と得点はそのまま。
     回答者は待っていれば自動でつながり直す）
6. 出題者の「ルール」から部屋のルールを変更できる:
   - **回答形式**: 「早押し」（既定）/「○×クイズ」/「4択クイズ」。
     ○×・4択は全員一斉回答: 受付開始→各自がタップで回答（締切まで変更可・
     他の人の回答は締切まで見えない）→出題者が締め切って正答を発表→**自動採点**。
     4択の選択肢は出題時に入力でき、回答者のボタンに表示されます
   - **問題の表示**: 「一括で表示」（既定）/「順次表示（読み上げ）」+ 読み上げ速度。
     順次表示では「早押し開始」と同時に問題文が流れ始め、**誰かが押すとその位置で停止**、
     再開放で続きから、正解確定で全文表示される（停止位置は host が権威として管理）
   - **押下音**: 「回答権を得た人だけ鳴る」（既定）/「押した全員に鳴る」
   - **得点**: 正解の得点（+1〜+10）と誤答のペナルティ（0〜−5）
   - **勝ち抜けライン**: 設定点数に達したプレイヤーに「勝ち抜け」表示
   - **得点を隠す**: 回答者には得点・順位を「?」で伏せ、結果発表で初めて公開する
     （出題者にはいつでも実際の得点が見えます）
   - **チーム戦**: 2〜4チーム。参加順で自動割り当て（タップで変更・シャッフル可）。
     チーム合計を表示し、不正解時は「他チームに開放」（誤答者のチーム全員を除外して再開放）が使える
   - **同名での復帰**: ON（既定）だと切断中の同名プレイヤーに得点ごと復帰できる。
     ルームコードと名前を知っていれば切断中の人になりすませてしまうため、
     気になる場合は OFF にする（OFF時はセッションIDでの復帰のみ）
   - **ハンデ**: プレイヤーごとに押下時刻へ加算する遅延（ms）。順位判定に反映され、
     全員の得点表に表示される

## 問題集（出題者の手元データ）

問題・答え・メモをまとめて管理できます。入口は2つあります:

- **トップ画面の「問題集を編集する」**: 部屋を開かずに編集する専用ページ。
  P2P 接続を持たないので、大きい画面でじっくり作り込んでも進行中の接続に影響しません
- **出題者画面の「出題」見出しの隣「問題集から選ぶ」**: 一覧の「選ぶ」で問題文・答え・
  選択肢が出題欄に読み込まれます（この時点ではまだ回答者には出ません）。
  内容を確かめて、必要なら直してから「問題を表示」で出題します

どちらも同じデータ（この端末の localStorage）を見ています。

- 追加・編集フォームは一覧の下端に貼り付いていて、いつでも開閉できます。
  一覧の「編集」を押すと、その問題の内容が入った状態でフォームが開きます
- 1問ずつの追加のほか、見出し右の「まとめて入れる・持ち出す」から
  **タブ区切りテキストの貼り付け取り込み**ができます（形式は下記「問題集の形式」を参照）
- 一覧から選んで出題。**答えとメモは出題者の画面にだけ表示**され、
  P2P には一切流れません（答えは判定結果になってから全員に表示されます）
- 「サンプルを取り込む」で早押し・○×・4択のサンプル問題をまとめて追加できます
- 取り込みは**同じ問題（形式+問題文が同じ）を重複して追加しません**。
  ファイルからの復元は既定で「今の問題集に足す」、チェックを入れると「空にして入れ替える」
- 出題すると**出題日時と正解者名が履歴に自動記録**されます（何回出題したかも見える）
- **AI に作らせる場合**: 形式ごとに「AI依頼文」ボタンがあり、そのまま使える依頼文を
  クリップボードにコピーできます（AI の出力をそのまま貼り付けられる形式で頼む文面）
- 保存は出題者のブラウザ内（localStorage）。**ブラウザ保存は消えることがある**
  （Safari は7日間未使用で削除、閲覧データ削除など）ため、
  **JSON ファイルへのエクスポートを正本**とし、「ファイルから復元」で戻す運用を推奨します。
  `navigator.storage.persist()` の要求と最終エクスポート日時の表示で消失リスクを下げています

## アーキテクチャ

- **スター型・host権威**: 出題者（host）が唯一の信頼できる状態
  （参加者・フェーズ・押下順・得点）を保持し、回答者（player）は host から配信された
  状態スナップショットを描画するだけです。player の自己申告値は一切信用しません。
- **押下順判定**: host⇔player 間で ping/pong を往復させて RTT とクロックオフセットを推定
  （複数サンプルの中央値）。player はボタン押下時の `performance.now()` を送信し、
  host がオフセットで host 時計に換算して順位を決めます。**到着順では判定しません**。
  受付開始（host時刻）より前に換算される押下はフライングとして無効です。
- **再接続**: player は sessionStorage のセッションIDで再参加すると得点を引き継ぎます。
  タブを閉じる等でセッションIDが変わっても、**切断中の同名プレイヤー**がいれば同一人物と
  みなして得点ごと復帰できます（接続中のプレイヤーの名前を使った乗っ取りはできません）。
  回答者画面は Wake Lock（対応端末のみ）で待機中の画面スリープによる切断も防ぎます。
- **出題者の復帰**: host は状態が変わるたびに進行状態（ルームコード・参加者と得点・ルール・
  出題履歴・現在の問題）を localStorage に保存し、リロードやタブを閉じた後でも
  トップ画面の「前の部屋に戻る」（または `#/host/<CODE>` の URL）から同じ部屋に復帰できます
  （保存はこの端末のみ・6 時間で無効）。時計に依存する早押しの受付中・判定待ちは
  「受付停止」と同じく問題表示中に戻して再開します。回答者は host が消えると
  「出題者との接続が切れました」と表示して戻りを待ち、同じルームコードで現れた host に
  自動で参加し直します（セッションIDが同じなので得点も引き継がれます）。
  出題者が「設定 → 部屋を閉じる」で明示的に終了した場合だけ、回答者に「部屋が終了しました」と出ます。

```
src/
├─ net/
│  ├─ transport.js         # 通信層インターフェース（join/leave/send/onMessage/onPeerJoin/onPeerLeave）
│  ├─ webrtc-transport.js  # RTCPeerConnection / DataChannel の自前実装（スター型を強制）
│  ├─ tracker-signal.js    # WebTorrent トラッカープロトコルの自前実装（シグナリング）
│  ├─ protocol.js          # メッセージ型定義とスキーマ検証
│  └─ timesync.js          # RTT / クロックオフセット推定（min-RTTフィルタ + 中央値）
├─ game/
│  ├─ phases.js      # フェーズ定義
│  ├─ buzz.js        # 押下順判定（純関数）
│  └─ host-game.js   # host 権威の状態機械
├─ ui/               # トップ / 出題者 / 回答者 画面（buzzer-styles.js: ボタンの見た目定義）
└─ assets/buzzer/    # 早押しボタンのスプライト（台とボタンで別画像）
```

早押しボタンは「台」と「ボタン」の 2 層で、押下時にボタン部分が沈むアニメーションになる。
効果音は押下・回答権獲得・正解/不正解・ロック通知（host側）を Web Audio で鳴らす。
スプライトは `assets-src/`（git 管理外）の参考画像から
`node scripts/extract-buzzer-sprites.mjs` で再生成できる。

マスコット「クイズ隼人」はトップ画面とファビコンにのみ表示している
（`node scripts/extract-mascot.mjs` で再生成）。

## 開発

```sh
npm install
npm run dev      # 開発サーバ（公開トラッカーへの接続にインターネットが必要）
npm test         # ユニットテスト（クロックオフセット推定・押下順判定）
npm run test:e2e # E2E テスト（dev サーバは自動起動。初回のみ npx playwright install chromium）
npm run test:all # 上記2つを続けて実行
npm run build    # docs/ に本番ビルドを出力
```

## テスト

- **ユニットテスト**（vitest / `tests/`）: クロックオフセット推定・押下順判定の純関数
- **E2E テスト**（Playwright / `e2e/`）: 実際に公開トラッカー経由で P2P 接続して検証する
  - 基本フロー: 部屋作成 → 参加 → 出題 → 早押し → 正解 → 得点 → 再接続の得点引き継ぎ → host切断表示
  - **複数端末**: 3人が別ブラウザコンテキスト（=別端末相当。うち1人は iPhone 相当の
    タッチエミュレーション）で同時参加し、ほぼ同時押しの押下順・ms差、
    不正解→次点へ、不正解→全員再開放（誤答者除外）、手動加減点の配信を検証
  - 公開環境に対して実行する場合: `$env:E2E_BASE_URL='https://<user>.github.io/<repo>/'; npm run test:e2e`
  - 本番ビルドに対して実行する場合: `npm run build` → `npm run preview` →
    `$env:E2E_BASE_URL='http://127.0.0.1:4517/'; npm run test:e2e`
- **CI**: GitHub Actions（`.github/workflows/test.yml`）が push / PR ごとに両方を実行する。
  E2E は公開トラッカー経由で実接続するため、稀に不安定な場合はリトライで吸収している。

`vite.config.js` で `base: './'`（相対パス）にしてあるため、
リポジトリ名がどんなサブディレクトリになっても動きます。

2. `docs/` をコミットしてプッシュ
3. GitHub のリポジトリ設定 → **Settings → Pages → Build and deployment** で
   Source: `Deploy from a branch`、Branch: `main` / `/docs` を選択
4. `https://<ユーザー名>.github.io/<リポジトリ名>/` で公開される

```sh
npm run build
git subtree push --prefix docs origin gh-pages
```

Settings → Pages で Branch: `gh-pages` / `/ (root)` を選択します。

## 制限事項

- **host（出題者）がいない間は進行できません。** 状態はすべて host が持っているため、
  host が切断すると player には「出題者との接続が切れました」と表示され、戻りを待つ状態になります。
  出題者はリロード・タブを閉じた後でも同じ端末なら「前の部屋に戻る」で復帰できますが、
  **別の端末からの引き継ぎはできません**（保存は端末ローカルのため）。
- **一部の回線・端末では P2P 直結を確立できない場合があります**（対称NAT・キャリア回線・
  iCloud プライベートリレー等）。緩和策として複数の STUN と、コミュニティ提供の
  ベストエフォート TURN 中継（Open Relay）をフォールバックに設定しています
  （`src/config.js` の `iceServers`。安定運用したい場合は自前の TURN に差し替え）。
- シグナリングに公開 BitTorrent トラッカーを使うため、トラッカーが全滅していると
  部屋の発見ができません。
- 対応ブラウザの目安は iOS 12 Safari 以降・モダンブラウザ全般です
  （ビルドターゲット safari12 + 最小ポリフィル + WebP 非対応時の JPEG 自動切替）。
  **古い iOS では標準の Safari を使うこと**（他ブラウザはマイクAPI非対応のため、
  接続に必要な「マイク許可」の互換手段が使えません）。

## 接続できない端末があるときのチェックリスト

0. 「接続できませんでした」画面の「診断情報」を開くか、「設定 → 接続診断を表示」で
   接続の経過ログが見られます。
   どの段階（トラッカー / offer・answer交換 / ICE）で止まったかで原因を絞れます
1. **古い端末（iOS 12 等）で接続できない場合**: 失敗画面に出る
   「**マイク許可で再試行**」をタップする（音声は使いません）。
   旧 Safari はマイク等の使用許可がないと LAN 内の接続候補を出さない仕様のため、
   同一 Wi-Fi でも直結できないことへの対処です。診断の「候補 … host=0」が目印。
   逆に出題者側の候補が mDNS 名（.local）で隠れている場合は、出題者の
   「ルール → 旧端末互換」を有効にする（実IPが有効な端末では「不要」と表示される）
2. 出題者と同じ Wi-Fi に接続する（最も確実）
2. iPhone の場合: 設定 → Wi-Fi → ネットワークの「IPアドレスのトラッキングを制限」をオフ、
   iCloud プライベートリレーを一時的にオフ、VPN をオフ
3. それでも繋がらない場合はモバイル回線⇔Wi-Fi を切り替えて再試行
4. 常に安定させたい場合は自前 TURN サーバを `src/config.js` の `iceServers` に追加

## 接続の設計

- **スター型を WebRTC レベルでも強制**: peer_id の先頭に役割（host/player）を埋め込み、
  回答者はホストの offer にしか answer しない。回答者どうしは接続しない
  （ただし接続情報はトラッカーが同じ部屋の全員に配るため、IP の秘匿にはならない。
  下記「セキュリティ / プライバシー」を参照）
- **双方向 offer で参加を即時化**: 参加者側も offer を announce するため、
  ホストの announce 周期を待たずに接続が始まる（典型 2〜5 秒で参加完了）
- 複数トラッカーへ並行 announce（1系統死んでも参加可能）+ 切断時は指数バックオフで再接続
- ICE は vanilla 方式（候補の収集完了を待って SDP に同梱。上限 1.6 秒で打ち切り）
- 同一ペアで両方向に接続が成立した場合は「offer した側の peer_id が小さい方を残す」
  決定的ルールで重複を解決
- クロックオフセット推定は RTT 下位半分のサンプルに絞って中央値を取り（min-RTTフィルタ）、
  混雑回線の非対称誤差を抑える

## 通信層の差し替え

通信は `src/net/transport.js` のインターフェースに抽象化してあります:

```js
{
  selfId: string,
  join(roomId): Promise<void>,
  leave(): void,
  send(msg, peerId?): void,   // peerId 省略時はブロードキャスト
  onMessage(cb(msg, peerId)),
  onPeerJoin(cb(peerId)),
  onPeerLeave(cb(peerId)),
}
```

別方式（自前シグナリングサーバや PeerJS 等）に切り替える場合は、この契約を満たす実装を
追加して `transport.js` の `createTransport()` を差し替えてください。
ゲームロジック側は通信方式を知りません。

## 問題集の形式

問題は3つの形式で登録でき、出題すると回答形式（ルール）も自動で切り替わります。

| 形式 | 入力する内容 | 回答者の画面 |
|---|---|---|
| 早押し | 問題文 / 答え / メモ | 早押しボタン。答えは出題者が目視で判定 |
| ○× | 問題文 / 正解（○か×） | ○ と × のボタン |
| 4択 | 問題文 / 選択肢1〜4 / 正解番号 | 選択肢つきの4つのボタン |

○×・4択を問題集から出題した場合は正解が分かっているため、締め切り後に
「正解を発表」のワンタップで自動採点されます。

貼り付け取り込み（1行1問・タブ区切り）は、**取り込む形式を選んでから**貼り付けます。
中身から推測しないのは、答えが「○」の早押し問題を ○× として取り込んでしまうなど、
誤判定が避けられないためです。

```
早押し:  問題	答え	メモ
○×  :  問題	○	メモ
4択  :  問題	選択肢1	選択肢2	選択肢3	選択肢4	正解番号	メモ
```

## セキュリティ / プライバシー

- ルームコードは `crypto.getRandomValues` による英数4文字（紛らわしい文字は除外）。
  招待した仲間内で使う前提で手入力のしやすさを優先しています（総当たりで部屋を
  見つけられる可能性はありますが、得点等の権威は出題者側にあります）
- **IP アドレスは相手に見えます**（WebRTC の仕組み上避けられません）。接続情報（SDP）に
  STUN で調べたグローバル IP が入るため、出題者と回答者は互いのグローバル IP を知り得ます。
  LAN 内の IP は現在のブラウザでは mDNS 名で隠されますが、「マイク許可で再試行」の
  互換モードでは実 IP が含まれます（同一 Wi-Fi 前提の機能）
- 回答者どうしは直接つながりませんが、トラッカーは同じ部屋の全員に接続情報を配るため、
  改造したクライアントなら他の回答者のグローバル IP を読めます。公開トラッカーの運営者も
  全員の IP と接続情報を見られる立場です（接続情報を書き換えれば理論上は中間者攻撃も可能。
  運営者を信頼する前提です）。気になる場合は VPN を使うか、自前 TURN を用意して
  `RTCPeerConnection` の `iceTransportPolicy: 'relay'` で中継を強制する改修をしてください
- 接続確立後の通信は DTLS で暗号化されます（DataChannel の標準）。ただし認証はないため、
  ルームコードを知っている人は誰でも参加でき、偽の参加で枠（24人）を埋めることもできます
- 押下時刻は回答者の自己申告（host が時計差を補正して比べる）なので、改造クライアントで
  常に1位を取るチートは防げません。得点・順位の権威は出題者側にあり、手動で加減点できます
- 端末のファイルを読む・コードを実行するといった攻撃は WebRTC 経由ではできません
  （ブラウザのサンドボックス内で、届くのは JSON 文字列だけです）
- 受信メッセージはすべてスキーマ検証してから処理（想定外の型・値は破棄。サイズ上限あり）
- 表示は `textContent` 経由のみ（innerHTML への文字列連結なし）
- ニックネームは表示専用。再接続時の再入力を省くためタブの sessionStorage にのみ保持し、
  タブを閉じれば消えます（localStorage には保存しません）
